# AMC 12 Practice API

This is the authenticated, server-authoritative backend for AMC 12 online
practice. It is deliberately separate from the static Markdown problem reader:
the static reader may continue to show solutions, while this API keeps answer
keys and solutions in PostgreSQL until a student has made a final submission.

## What it implements

- Access-code login with a signed, `HttpOnly` session cookie and a signed,
  SameSite CSRF token.
- Published-form listing and redacted questions for signed-in students only.
- A server clock with pause/resume. Only active elapsed time counts toward the
  form's 75-minute limit.
- One preliminary score slot (`CHECKPOINT` or automatic `DEADLINE`) and one
  immutable `FINAL` score slot. A manual checkpoint therefore suppresses the
  duplicate 75-minute snapshot, but never the 75-minute notice.
- Atomic deadline reconciliation, idempotent mutations, attempt row locks, and
  a polling deadline worker that works when a browser is closed.
- Reset-as-history: reset closes the old attempt and creates a new one; no
  answer, timer event, or submission is deleted. A reset historical attempt
  remains readable to its owner after it has a `FINAL` submission.
- Version-pinned attempt content: an attempt always retrieves the form revision
  it started with, even after a newer form revision is published.
- Partial per-question reasoning notes with optimistic revision checks. Notes
  follow the same running timed/overtime edit rules as answers and are frozen
  into a separate learning-submission snapshot only at final submission.
- An atomic learning-submission intent on final/deadline-final. Analysis remains
  explicitly `BLOCKED_CONTEXT` until reviewed multi-solution context is loaded;
  a leased PostgreSQL worker then produces independent per-question outcomes
  and a durable report. No external provider call can affect official scoring.
- Operator-published, untimed `OPEN_REVIEW` workspaces for separately released
  unpublished form revisions. Their blank v1 anchor has no timer, mutable
  answers, official submission, or AI work; a confirmed batch creates v2 and
  enters the same immutable report pipeline as an interactive final.

The default scoring policy is supplied by a form revision, never globally
hard-coded. The synthetic fixture uses legacy AMC practice values: correct = 6,
blank = 1.5, incorrect = 0.

## Run locally

```sh
cd AMC12_Problems/practice-api
cp .env.example .env
npm install
npm start
```

`npm start` runs pending PostgreSQL migrations before binding to
`127.0.0.1:8090`. Set `AMC12_DATABASE_URL` first. For a local access code, set
`AMC12_DEV_ACCESS_CODE` and optionally `AMC12_DEV_STUDENT_NAME`; production
does not permit this bootstrap behavior.

Create durable access codes with:

```sh
AMC12_NEW_ACCESS_CODE='replace-me' npm run create-access-code -- --name 'Student name'
```

Use an environment variable rather than `--code` so a secret is not placed in
shell history.

## Import content safely

Production content, and the default importer configuration in every
environment, accept only the reviewed `amc-practice-private-form-v1` artifact
generated by the sibling `practice-content` release gate. Keep private JSON
outside static hosting and outside the frontend build.

```sh
npm run import-form -- /protected/path/private-form.json --publish
```

For private v1 input, the API validates all of the following before any write:

- exact schema version, 25 ordered A–E questions, source references, answer
  choices, and non-empty solutions;
- `durationSeconds: 4500` → internal `durationMs: 4500000`;
- `publicationStatus`, synthetic status, policy version, policy max score, and
  explicit content revision (`version`);
- Python-pipeline canonical `contentHash` and `manifestHash` (sorted compact
  JSON, UTF-8, final newline);
- preservation of `sourceManifestHash`, `contentHash`, `questionBundleHash`,
  source schema version, publication status, and provenance in the revision
  audit record.

An approved manifest is still not visible until the explicit `--publish` flag
is present. Review-required private v1 content is rejected. Synthetic/test-only
content uses two independent development-only gates:

```sh
# Import privately but keep invisible to students
npm run import-form -- fixture-private.json --allow-test-only-import

# Permit a development-only visible synthetic form; --publish is still needed
npm run import-form -- fixture-private.json --allow-test-only-import --allow-test-only-publish --publish
```

Equivalent environment settings are `AMC12_ALLOW_TEST_ONLY_IMPORT=true` and
`AMC12_ALLOW_TEST_ONLY_PUBLISH=true`. Both are hard-disabled when
`NODE_ENV=production`. This is intentionally a second gate after the content
pipeline's own test-only guard.

The legacy/generic manifest adapter is retained solely for deliberate local
experiments and adapter tests. It is off by default, hard-disabled in
production, and requires either `AMC12_ALLOW_GENERIC_MANIFEST_IMPORT=true` or
the one-shot non-production CLI flag `--allow-generic-manifest-import`. It
must never be used as a shortcut around the reviewed private-v1 release gate.

### Historical archive-practice batch

The separately authorized historical archive uses a strict
`amc-practice-archive-form-v1` schema: it records that scores are archive
practice scores, preserves source/key/media provenance, and can mark an
unmatchable historical item as unscored. It is not accepted by the generic
adapter. Import the generated private batch atomically:

```sh
npm run import-archive-release -- \
  /protected/path/archive-release.private.json --publish
```

The importer validates every form before opening its one database transaction,
then imports all forms together. It rejects a partial batch, remote/unknown
schema, synthetic content, invalid score maximums, changed content hashes, or
a missing archive authorization record. The client receives the archive notice
and unscored-item marker, but never a key or solution before final submission.
For canonical AMC 12 archive ids it also enforces the historical scoring
boundary: 2002--2006 forms use 6/2.5/0 (correct/blank/incorrect), while
2007--2025 forms use 6/1.5/0.

### Approved AI context and learning worker

Reviewed AI context has a separate private artifact and import path. The
importer accepts only the exact single-form/archive approved v1 schemas,
recomputes canonical decision/content hashes, accepts bounded valid UTF-8
Markdown/HTML/link/TeX only as quoted model input, requires at least two
model-eligible human-approved solutions per ready question, and binds
prompt/choices to the already imported immutable form revision. Questions or
solutions that reference unavailable visuals remain explicitly unavailable to
the model. Model output is separately constrained to renderer-safe text:

```sh
AMC12_APPROVAL_AUTHORITY_IDS=approval-authority:production \
  npm run import-approved-context -- \
  /protected/path/approved-context.json \
  /protected/path/authority-receipts.json
```

This import is not a public API. It atomically supersedes the active context for
that exact form revision and repairs matching `BLOCKED_CONTEXT` work. Both
inputs must be owner-owned mode `0600` regular files inside a real owner-owned
mode `0700` directory; symlinks, FIFOs, duplicate JSON keys, invalid UTF-8, and
oversized input are rejected. The external receipt file and deployment
authority allowlist are part of the operations trust boundary (TCB): canonical
SHA-256 hashes provide integrity binding, not a cryptographic signature or
proof of who approved a solution. Protecting their ACL and provenance is
therefore mandatory.

After an unpublished form has complete approved context for every question,
an authenticated operator may publish it to the separate open-review catalog:

```sh
AMC12_OPEN_REVIEW_OPERATOR_ID='operator:curriculum-release' \
  npm run manage-open-review -- publish \
  <form-id> <form-version> <approved-context-set-uuid> <reason-code>

AMC12_OPEN_REVIEW_OPERATOR_ID='operator:curriculum-release' \
  npm run manage-open-review -- supersede <release-uuid> <reason-code>

AMC12_OPEN_REVIEW_OPERATOR_ID='operator:security-response' \
  npm run manage-open-review -- revoke <release-uuid> <reason-code>
```

This is intentionally an operator/store command, not a public administration
route. Publication permanently binds the exact form revision, question-bundle
hash, approved context set/hash, approval authority, and release hash. A form
revision or any clone with the same question bundle can be delivered either as
timed practice or open review, never both; PostgreSQL advisory locks and row
triggers enforce this during concurrent publication/attempt creation. A
partial unique index additionally permits at most one `ACTIVE` open-review
release for a question-bundle hash, including releases under distinct form IDs.

`ACTIVE` permits new workspaces and new batches. `SUPERSEDED_VALID` permits
existing workspaces, batch completion, reports, and their pinned context, but
not new workspaces or batches. `REVOKED` blocks protected analysis immediately,
cancels leased inference, and preserves only exact-lineage provider/local
cleanup authority. Owner-submitted/confirmed evidence remains visible, while
deterministic result fields and reports are withheld. Revocation guarantees
that no new provider authorization begins after the revoke commits and that no
later completion is accepted. A call authorized before that commit may already
be in flight and may still reach the provider; cancellation is best-effort, so
the completion fence—not a physical zero-call claim—is the security boundary.
Deleting transient upload/provider data is not deletion of
the student's immutable learning submission or report; those need a separate
product retention/deletion policy.

The operator CLI intentionally keeps successor publication as two auditable
steps: supersede the predecessor, then publish the successor. Between them the
active catalog is fail-closed and may temporarily contain no release for that
bundle. Operators must audit both append-only events; the system does not invent
a successor link when the second command fails.

Start the durable analyzer as a separate process after configuring its
dedicated loopback Gateway token, independent `AMC12_AUTH_PEPPER`, absolute
`AMC12_PRIVATE_UPLOAD_ROOT` outside the source/static tree, and provider secret:

```sh
npm run start:learning-worker
```

The browser and persisted work cannot select a URL, model, tool, or generation
control. Tutor completion validates `AMC12_INFERENCE_MODEL` against the
operator-pinned Gateway model. The unified AI dispatcher uses only
`POST /v1/tutor-turn`, `POST /v1/analyze-question`, and
`POST /v1/decompose-batch` on the configured loopback origin, reserves at least
one concurrency slot for non-Tutor work, and sends only model-eligible approved
solutions. Within that slot, a PostgreSQL-persisted class cursor alternates
eligible interactive-analysis and batch-extraction claims across worker
processes. Class-local priority remains the normal latency preference, but a
work item ready for two minutes enters an overdue FIFO tier so sustained
higher-priority arrivals cannot prevent either interactive or batch-confirmed
reports.
Analysis/batch handlers heartbeat their leases during provider calls. Tutor
instead requires a lease covering the fixed Gateway timeout plus a persistence
margin, rechecks the remaining lease after durable dispatch intent, and never
replays an uncertain delivery. All handlers reject stale completion writes.
Analysis and batch work use bounded exponential backoff; Tutor creates an
automatic retry only when the Gateway strictly proves `KNOWN_NO_RESULT`.
The paired Gateway must retain its frozen `AMC_INFERENCE_MAX_BODY_BYTES=524288`
minimum/default; the API performs the same 524,288-byte serialized-request
preflight, including the worst valid eight-solution escaped payload.

`COMPLETE` is scoped to every question in one immutable learning-submission
version, not to every question on the source form. A confirmed batch therefore
can be `COMPLETE` after all of its mapped questions are analyzed while its score
continues to declare `scoringScope=MAPPED_QUESTIONS_ONLY` and an explicit
`mappedQuestionCount`; clients must not label that state as whole-form review.

### Prerecorded audio transcription adapter

Batch audio is transcribed by a server-side AssemblyAI prerecorded adapter; the
browser never receives the provider credential. Supply the credential through
the dedicated worker's secret injection as `AMC12_ASSEMBLYAI_API_KEY` and keep it out
of source, `.env.example`, database rows, job payloads, logs, and audit events.
The key disclosed during design is compromised by disclosure and must be revoked
and replaced before any deployment or live test. The adapter fixes the provider
origin to `https://api.assemblyai.com`, rejects redirects, accepts at most 25
MiB per audio asset, uses language detection with the fixed prerecorded speech
model fallback list, and allows at most one hour of provider-reported audio.
Text files do not pass through this adapter.

Submission is intentionally split across durable worker leases. Before upload
and transcript creation, the worker commits separate `MAY_HAVE_DELIVERED` call
barriers. It never blindly repeats an ambiguous call. A known transcript ID is
committed before a later invocation may poll it; polling has independent
business attempt/age limits, while provider and local deletion retries remain
durable and are not capped by that business limit. A completed transcript is
validated, bounded to 256 KiB, normalized into private durable evidence, and
scheduled for an explicit provider DELETE. Provider IDs are operational cleanup
identifiers only and must not be exposed to the student.

AssemblyAI upload URLs are not persisted: only their SHA-256 is retained for
exact reconciliation. Every deployment explicitly attests one retention
profile (`CONFIGURED_TTL`, `BAA_DEFAULT`, or `NO_TTL_OR_BAA`), its policy delay,
and a separate processing-lag slack. The durable not-before is the pre-call
barrier plus the full upload timeout, policy delay, and slack; missing or
inconsistent production configuration prevents worker startup. An ambiguous
transcript submission pages the fixed
provider list API over the bounded UTC-day window, compares the exact upload
URL hash, and schedules every match for deletion; an incomplete scan or a
90-day unresolved result remains visibly manual-blocked rather than being
declared absent. If a known transcript cannot be bound, its exact ID is first
persisted in the independent orphan cleanup queue—there is no unfenced
best-effort DELETE. Provider DELETE calls use a separate global emergency
`PROVIDER_CLEANUP` budget and never consume or wait on a student's business
provider quota. An ambiguous upload immediately schedules durable local-audio
purge; it never waits for the upstream retention window. When that conservative
window elapses, the system records only `PROVIDER_RETENTION_WINDOW_ELAPSED` and
leaves the artifact and batch `PROVIDER_RETENTION_PENDING`. `COMPLETE` requires
a later independent operator/provider confirmation with an audited reference
hash. A window timer is an account-policy attestation, never physical-deletion
evidence.

Provider deletion is data minimization, not proof that no upstream retention or
logging exists. AssemblyAI documents that asynchronous retention varies by
account configuration and that AWS TTL processing after expiry can lag from
hours to days; see its [data retention documentation](https://www.assemblyai.com/docs/data-retention-and-model-training).
Production remains blocked on independent confirmation of the AssemblyAI
account's retention, regional processing, training, subprocessors, DPA, and
deletion behavior. The application must keep its own immutable student
submission/report retention policy separate from transient provider cleanup and
must expose product-level deletion/export rules explicitly.

## API contract

Base path: `/api/amc12`. JSON errors use:

```json
{"error":{"code":"INVALID_STATE","message":"…"}}
```

`POST /auth/login` takes `{ "accessCode": "…" }`, sets signed cookies, and
returns `{ student, csrfToken }`. Send `X-CSRF-Token: <csrfToken>` and browser
credentials on every authenticated state-changing request.

| Endpoint | Purpose |
| --- | --- |
| `GET /auth/me`, `POST /auth/logout` | Restore/end session |
| `GET /forms`, `GET /forms/:formId` | Authenticated published catalog/content, redacted |
| `GET /forms/:formId/versions/:version` | Authenticated published pinned revision |
| `GET /open-reviews`, `GET /open-reviews/:releaseId` | Active open-review catalog and prompt/choice-only exact revision |
| `POST /open-reviews/:releaseId/workspace` | CSRF + `Idempotency-Key`; atomically create/replay one blank v1 workspace |
| `GET /open-review-workspaces`, `GET /open-review-workspaces/:attemptId` | Owner-only open-review history/detail |
| `POST /attempts`, `GET /attempts`, `GET /attempts/:id` | Start/recover/list attempts |
| `GET /attempts/:id/form` | Owner-only, exact revision used by this attempt |
| `PUT /attempts/:id/answers` | Save selected A–E/null answers with optional optimistic `revision` |
| `GET`, `PUT /attempts/:id/reasoning-notes` | Read/save owner-only partial reasoning notes; PUT requires CSRF, `Idempotency-Key`, and reasoning `revision` |
| `POST /attempts/:id/pause`, `/resume` | Pause/resume active timer |
| `POST /attempts/:id/checkpoint` | One immediate preliminary score; body includes current expected revisions |
| `POST /attempts/:id/final` | Manual final submission before/after overtime; body includes current expected revisions |
| `POST /attempts/:id/deadline-decision` | `{ "decision": "continue" \| "finalize", "expectedAnswersRevision", "expectedStateRevision" }` at 75 minutes |
| `POST /attempts/:id/reset` | Preserve old history and return a new `TIMED` attempt |
| `GET /attempts/:id/results`, `/solutions` | Owner-only after a final submission (also for reset history) |
| `GET /attempts/:id/learning-submission` | Read-only owner status after final; never performs historical repair while polling |
| `GET /attempts/:id/learning-report` | Read-only owner report/status after final, including reset history; never enqueues analysis |
| `GET /learning-history` | Bounded owner-only keyset page across timed, batch, and open-review lineages, including every immutable version summary |
| `GET /learning-history/:submissionId` | Exact owner-only lineage detail; deleted records return only minimal tombstone metadata |
| `GET /learning-history/:submissionId/versions/:versionNumber/questions/:questionNumber` | Exact-version prompt, choices, own evidence, deterministic result, and analysis subject to release/deletion policy |
| `GET /learning-history/:submissionId/versions/:versionNumber/report` | Exact immutable report; blank anchors are unavailable and revoked/deleted protected content fails closed |
| `GET`, `POST /learning-history/:submissionId/versions/:versionNumber/questions/:questionNumber/tutor-threads` | List or idempotently create owner-only question threads from server-derived immutable context |
| `GET`, `DELETE /learning-history/:submissionId/versions/:versionNumber/questions/:questionNumber/tutor-threads/:threadId` | Read or idempotently tombstone one exact-path thread |
| `POST /learning-history/:submissionId/versions/:versionNumber/questions/:questionNumber/tutor-threads/:threadId/messages` | Queue one bounded student message; the browser supplies no context/model/hash fields |
| `POST /learning-history/:submissionId/versions/:versionNumber/questions/:questionNumber/tutor-threads/:threadId/forks` | Explicitly fork from the Store-selected current successful head |
| `POST /learning-history/:submissionId/versions/:versionNumber/questions/:questionNumber/tutor-threads/:threadId/requests/:requestOrdinal/retries` | Explicitly retry one visible terminal request ordinal; no internal job ID crosses the API |

The learning-submission status GET is strictly read-only; missing historical
aggregates are repaired only through the internal maintenance entrypoint. The
reasoning-notes GET intentionally retains the existing attempt read-and-
reconcile semantics: crossing the server deadline during that read records the
same deadline transition as `GET /attempts/:id`, then returns `editable=false`.
Learning-history GETs are pure projections: they neither repair/enqueue state
nor call a provider, and all success/error responses are explicitly `no-store`.
Tutor routes are absent unless `AMC12_TUTOR_ENABLED=true`; the same flag must be
enabled in the independently configured learning worker only after the Gateway
and durable crash-window checks pass.

`reasoning-notes` PUT, `pause`, `resume`, `checkpoint`, `final`, `deadline-decision`, and `reset`
require an `Idempotency-Key` (8–128 opaque characters). Replaying the same key
and request does not repeat its mutation; reusing it with different input is a
409 conflict. Reasoning-note replays rebuild the current owner-scoped envelope
so student prose is not copied into the generic idempotency ledger. Other
mutations return their stored original response.

Every score-producing request (`checkpoint`, `final`, and either deadline
decision) must include the exact non-negative `expectedAnswersRevision` and
`expectedStateRevision` from the attempt the student reviewed. The service
atomically rejects a stale tab with `ANSWER_REVISION_CONFLICT`; it never scores
another tab's unseen answer sheet.

An attempt response has `phase` (`TIMED`, `LIMIT_NOTICE`, `OVERTIME`,
`FINALIZED`, `RESET`), `clockState` (`RUNNING`, `PAUSED`), server-derived
`activeElapsedMs`/`remainingMs`, `answersRevision`, `reasoningRevision`, monotonic `stateRevision`,
redacted answer selections, and public submission summaries. Clients use
`stateRevision` to discard a delayed response that predates a saved answer,
deadline decision, reset, or final submission. `resultsAvailable` is true only
when that attempt's immutable history has a final submission.

At 75 active minutes, the server atomically creates a `DEADLINE` preliminary
submission only when no `CHECKPOINT` exists, changes phase to `LIMIT_NOTICE`,
and stops the active clock. The UI must ask whether to finalise or continue.
Choosing continue starts `OVERTIME`, which is intentionally not auto-submitted;
the student must later finalise.

## Deployment and proxy safety

The normal listener is loopback-only and assumes workspace Nginx forwards it.
`AMC12_TRUST_PROXY` defaults to `loopback`, so Fastify uses the client IP that
Nginx supplies for login rate limits. Nginx must **overwrite**, not append,
client forwarding headers from untrusted requests, for example:

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Real-IP $remote_addr;
```

If the API is bound directly to a public interface, set
`AMC12_TRUST_PROXY=false`; otherwise clients could spoof `X-Forwarded-For`.
Use HTTPS in production (`AMC12_SECURE_COOKIES=true`). The API's CORS setting
is opt-in and should be one exact origin; same-origin reverse proxy deployment
is preferred.

## Storage

All tables live in the isolated `amc_practice` schema. Important records are:

- form revisions/questions and pipeline audit hashes/provenance;
- students, hashed access-code lookup values, and revocable sessions;
- attempts/current answers/timer events;
- immutable open-review releases and append-only lifecycle events;
- current reasoning notes (student prose is not duplicated into idempotency records);
- immutable submissions and 25-row answer snapshots for each submission;
- learning submissions, immutable evidence versions/question responses, and
  durable `BLOCKED_CONTEXT`/leased analysis work;
- approved context sets/questions/solutions with release, candidate, decision,
  reviewer, rights, source, and content-hash lineage;
- analysis runs, per-question outcomes, allowlisted run metadata, and redacted
  aggregate learning reports;
- idempotency records.

Answer keys are only queried by scoring and final-result/solution paths. No
pre-final form or attempt response serializes `correctOption`,
`solutionMarkdown`, source references, or raw private-manifest URLs.

## Verification

```sh
npm test
npm run test:integration
AMC12_TEST_DATABASE_URL='postgres://…/amc_practice_test' npm run test:integration
```

The PostgreSQL smoke test is intentionally skipped without
`AMC12_TEST_DATABASE_URL`; when configured it runs migrations twice, imports a
freshly generated `practice-content` synthetic private artifact, verifies audit
hash/provenance persistence, imports approved context, races two worker pools
with `SKIP LOCKED`, reclaims an expired lease, rejects the stale writer, and
verifies a 25-question report without changing the official score. It also
checks open-review database invariants, official-table isolation, concurrent
same-key workspace creation, and two-pool release-vs-timed/published delivery
fences for cloned question bundles.

The API validates content hashes for integrity, not artifact provenance signing:
private manifests and approved-context artifacts still need protected release
storage and a trusted import operator. Add signatures/KMS verification if
artifacts cross an untrusted boundary.
